## 1. システム概要

### 1.1 一言でいうと

**Gmailを保管庫として使う、サーバーを持たないチャットアプリ。** メッセージはすべて普通のメールとして送受信され、Gmailの中に残ります。らくらくメールはそれをチャットの見た目で表示し直す「ビューア兼エディタ」です。

### 1.2 構成

```
┌─────────────────────────────┐
│ 利用者のブラウザ                                │
│  ┌───────────────────────┐  │
│  │ らくらくメール (React SPA / PWA)         │  │
│  │  ・画面表示                              │  │
│  │  ・メールの組み立てと解釈                │  │
│  │  ・設定データの暗号化                    │  │
│  └───────────┬───────────┘  │
│              │ IndexedDB（暗号化した設定）      │
└──────────────┼──────────────┘
               │ HTTPS（ブラウザから直接）
    ┌──────────┼──────────┐
    ▼                     ▼                     ▼
┌────────┐  ┌────────┐  ┌────────┐
│ Gmail API    │  │ Drive API    │  │ Google       │
│ メール送受信 │  │ appDataFolder│  │ Identity     │
│ ラベル/フィルタ│  │ 設定の同期   │  │ ログイン     │
└────────┘  └────────┘  └────────┘

配信元: GitHub Pages（静的ファイルのみ / D-01）
サーバー: なし
```

### 1.3 用語

| 用語 | 意味 |
| --- | --- |
| **パネル** | 1人の相手、または1つのグループとのやり取りを表示する画面領域（SND-01） |
| **会話（Conversation）** | 1つのパネルに対応するやり取りの単位。内部的に会話ID（UUID）を持つ |
| **スレッド** | Gmail側のメールのまとまり。Gmail APIの `threadId` で識別される |
| **らくらくメール利用者** | 独自ヘッダ付きのメールを送ってきたことがある相手 |
| **未利用者** | 上記以外の相手。普通のメールソフトを使っている |
| **目印** | Gmailの検索・フィルタで拾うために本文フッタへ入れる文字列（D-16） |

| 言語・FW | TypeScript + React | D-03 |

| 配信 | GitHub Pages。サーバー処理は一切なし | D-01 |
| インストール | PWAとしてホーム画面に追加可能。ストア配信なし | D-02, NFR-05 |
| 表示言語 | 日本語のみ | D-05 |

### 2.2 対応環境（NFR-06）

| 環境 | 対応レベル |
| --- | --- |
| Chrome（Windows PC） | 動作保証 |
| Edge（Windows PC） | 動作保証 |
| Chrome（Android スマホ） | 動作保証 |
| Chrome（Android タブレット） | 動作保証 |
| Safari（iPhone / iPad / Mac） | ベストエフォート |

**既知の制約（D-13）:** iPhone/iPad Safari はサードパーティCookieの制限が厳しく、Googleのトークンを裏で取り直せずログイン画面が出る頻度が上がる可能性があります。ベストエフォート対応のため、発生しても仕様とします。

### 2.3 認証

Google Identity Services（GIS）のトークンモデルを使います。サーバーが無いためリフレッシュトークンは発行されません（D-09）。

**流れ:**

1. 起動時、`requestAccessToken({ prompt: '' })` で**画面を出さずに**トークン取得を試みる
2. 成功すればそのまま利用可能（Googleにログイン中であれば通常はここで成功する）
3. 失敗した場合のみ、Googleのログイン／同意画面を表示する
4. トークンは**メモリ上のみに保持**する。IndexedDBにもlocalStorageにも書かない（D-54）
5. 有効期限（約1時間）が近づいたら、2〜3を繰り返して自動で取り直す

**アカウント切り替え（D-36）:** アカウントごとに独立したトークンを保持します。切り替え時、対象アカウントのトークンが無ければ `login_hint` にそのアドレスを指定して取得します。同時表示（統合受信）は行いません。

### 2.4 使用するAPIとスコープ

| スコープ | 区分 | 用途 | 段階 |
| --- | --- | --- | --- |
| `gmail.modify` | 必須 | メールの読み取り、送信、ラベル付与、ゴミ箱への移動、送信者名の読み取り | M1〜 |
| `userinfo.profile` | 任意 | Googleアカウントの名前を読み、自分の表示名を自動で埋める（D-64） | M1〜 |
| `gmail.settings.basic` | 必須 | フィルタとラベルの自動作成（D-18） | M2〜 |
| `drive.appdata` | 必須 | 設定データの端末間同期（D-50） | M6〜 |
| `contacts.readonly` | 任意 | Gmail連絡帳から相手を選ぶ（FUN-02 / P2） | M3〜（後回し可） |

**必須と任意の区別（D-64）:** 同意画面ではスコープごとにチェックを外せます（granular consent）。**任意**のスコープを外されてもログインは成立させ、機能を落とすだけにします。**必須**のスコープが欠けた場合のみログインを失敗させます。

- `[検証済み 2026-09-01]` `users.messages.send` は **`gmail.modify` だけで実行できます**（M1 Step 3 で実送信して確認）。`gmail.send` の追加は不要です（D-65）。
- `[検証済み 2026-09-01]` `users.settings.sendAs.list` の**読み取り**は `gmail.modify` に含まれます（M1 Step 2 で確認）。書き込み（フィルタ・ラベルの作成）には `gmail.settings.basic` が別途必要です。
- `[要調査 / D-53]` `drive.appdata` の追加が、将来の一般公開審査（D-07）の範囲に与える影響を M6 着手前に調べます。

**自分の表示名の決め方（D-64 / NFR-01）:** 利用者に入力させないため、次の順に自動取得します。

1. `users.settings.sendAs.list` の主アドレスの `displayName`（Gmailが送信時に From へ入れている名前）
2. `userinfo` の `name`（Googleアカウントの名前）。1が空のとき Gmail が実際に使う名前
3. どちらも取れなければ入力してもらう

この文字列は件名（3.4）に入り、会話を通じて変わりません。

### 2.5 Google審査の運用（D-07, D-08）

- OAuth同意画面は当面**テストモード**とし、利用者10人程度のGmailアドレスをテストユーザーとして登録します。
- 初回ログイン時に「このアプリは Google で確認されていません」という警告画面が出ます。**通過手順を図入りで説明した案内ページをアプリ内に用意**します（NFR-01）。
- 一般公開に移行する場合は、Googleの審査に加えて第三者セキュリティ審査（CASA）が必要になります。

## 3. Gmail連携仕様

**本章が本システムの中核です。** 「チャットに見えるが実体はメール」を成立させるための取り決めを定めます。

### 3.1 目印文字列（D-15, D-16, D-17, D-31）

Gmailは独自ヘッダを検索・フィルタで扱えません。そのため**本文フッタに入れる目印文字列だけが、Gmailの機能でらくらくメールのメールを選び出す唯一の手段**です。

| 種別 | 目印 | 用途 |
| --- | --- | --- |
| 通常メッセージ | `rakurakumail` | らくらくメールのメール全般を拾う |
| リアクション | `rakurakumail` ＋ `rakurakureact` | リアクションだけを別扱いにし、受信トレイをスキップさせる（D-30） |

ハイフンを含めないのは、Gmailの検索が単語の区切りとして扱う場合があるためです（D-17）。

### 3.2 本文フッタ

**通常メッセージ:**

```
（本文）

--
らくらくメール rakurakumail より送信
```

**リアクション（未利用者にも文脈が伝わるようにする / D-32）:**

```
👍

（「明日の10時でお願いします」への反応です）

--
らくらくメール rakurakumail より送信（リアクション: rakurakureact）
```

- 引用する元メッセージは**先頭30文字まで**とし、超える場合は末尾に「…」を付けます。
- `[要承認]` リアクションのフッタ文面。`rakurakureact` を含める必要は技術的に必須ですが、表現は変更可能です。

### 3.3 独自ヘッダ

送信時に付与します。日本語・絵文字・配列を含む値は、ヘッダがASCIIしか扱えないため `X-Rakuraku-Meta` にまとめてJSONをbase64url符号化して格納します。

| ヘッダ | 値 | 必須 |
| --- | --- | --- |
| `X-Rakuraku-Version` | `1`（形式の版数） | ○ |
| `X-Rakuraku-Type` | `message` / `reaction` / `system` | ○ |
| `X-Rakuraku-Conv-Id` | 会話ID（UUIDv4） | ○ |
| `X-Rakuraku-Msg-Id` | このメッセージのID（UUIDv4）。リアクションの宛先指定に使う | ○ |
| `X-Rakuraku-Group-Id` | グループID（UUIDv4） | グループのみ |
| `X-Rakuraku-Meta` | 下記JSONのbase64url符号化 | ○ |

`X-Rakuraku-Meta` のJSON:

```jsonc
{
  "sender":   { "name": "芝 直之" },              // 表示名
  "group":    {                                    // グループのときのみ
    "name": "家族",
    "rosterVersion": 3,                            // メンバー表の版数（D-43）
    "members": [ { "email": "...", "name": "..." } ]
  },
  "reaction": {                                    // Type=reaction のときのみ
    "targetMsgId": "（対象のX-Rakuraku-Msg-Id）",
    "emoji": "👍"
  },
  "images": [ { "cid": "...", "name": "..." } ]    // 画像を本文中に並べる順序
}
```

**版数の扱い:** 受信側は `X-Rakuraku-Version` が自分の知らない値だった場合、解釈できる範囲だけを使い、残りは本文テキストとして表示します（将来の形式変更で古い版が壊れないようにするため）。

**`[検証済み 2026-09-01]` Gmail は独自ヘッダを保存します。** M1 Step 3 で Gmail から Gmail へ実送信し、受信側のソースに `X-Rakuraku-Version` / `Type` / `Conv-Id` / `Msg-Id` / `Meta` の5つがすべて残ることを確認しました。本章の設計は成立します。

**`[既知の制約]`** 独自ヘッダは DKIM の署名対象（`h=`）に含まれません。Gmail 同士では問題ありませんが、他社のメールサーバーを経由する場合に落とされない保証はありません。落ちた場合その相手は「未利用者」として扱われるだけで（3.9）、会話の取り込みは `threadId`（D-20）と本文の目印（3.1）で成立するため、致命的にはなりません。

### 3.4 件名（D-59）

Gmailはスレッドをまとめる際に件名も見るため、**1つの会話では件名を変えません。** 会話を開始した人が決めた件名を、参加者全員がそのまま使い続けます。

| 種別 | 形式 | 例 |
| --- | --- | --- |
| 1対1 | `らくらくメール（<開始した人の表示名>）` | `らくらくメール（芝 直之）` |
| グループ | `らくらくメール（<グループ名>）` | `らくらくメール（家族）` |

- 返信時は Gmail / メールソフトの慣習どおり `Re: ` が付きますが、同一スレッドとして扱われます。
- この件名は**相手の受信箱に表示される文字列**です。上記の形式で確定しました（D-59 / Q-31=1）。
- 日本語を含むため、送信時は **RFC2047**（`=?UTF-8?B?<base64>?=`）で符号化します。メールヘッダはASCIIしか通らないためです。
- 会話を通じて固定であるため、**あとから表示名を変更しても既存の会話の件名は変わりません。**

### 3.5 ラベルとフィルタ（D-18, SND-10, SND-11）

初回セットアップ時に、**確認画面を出したうえで**アプリが自動作成します。

**ラベル:**

| ラベル | 用途 |
| --- | --- |
| `らくらくメール` | らくらくメールのメール全般 |
| `らくらくメール/リアクション` | リアクションのメール |

**フィルタ:**

| # | 条件（Gmail検索式） | 動作 |
| --- | --- | --- |
| F1 | `"rakurakumail"` | ラベル `らくらくメール` を付ける |
| F2 | `"rakurakureact"` | ラベル `らくらくメール/リアクション` を付ける ＋ **受信トレイをスキップ**（D-30） |

- Gmailのフィルタは**既存のメールには遡って適用されません。** 初回取り込みは 3.7 の検索で行います。
- 自分が送信したメールにはフィルタが適用されません。送信直後に `messages.modify` でラベルを付けます（SND-10 / 3.6）。
- F2により、相手もらくらくメール利用者であればリアクションで通知が鳴りません。**未利用者のGmailでは通常どおり通知が鳴ります（D-33）。**

### 3.6 送信手順

1. 会話の情報（会話ID・件名・継続中のスレッドID）を取得する。無ければ新規に採番する
2. MIMEメッセージを組み立てる
   - 画像・添付があれば `multipart/mixed`、無ければ `text/plain; charset=UTF-8`
   - 本文＋フッタ（3.2）
   - 独自ヘッダ（3.3）
   - 継続の場合は `In-Reply-To` と `References` に直前のメッセージIDを設定
3. `users.messages.send` を実行する。継続の場合は `threadId` を指定する
4. 応答の `id` に対して `users.messages.modify` でラベル `らくらくメール`（リアクションなら `らくらくメール/リアクション` も）を付ける
5. 会話情報のスレッドIDと最終メッセージIDを更新して保存する

**長いスレッドの分割:** 1スレッドのメッセージ数が **100通**を超えたら、次の送信から新しいスレッドを開始します（件名は同じ、`In-Reply-To` は付けない）。会話は複数のスレッドIDを保持できる構造にします（4.2）。Gmail側が長大なスレッドを分割することがあるための対策です。

**グループ送信（D-39, D-43）:**

- 宛先はメンバー全員を `To` に入れます（`Bcc` は使いません。相手が全員に返信できる必要があるため）
- `X-Rakuraku-Meta.group.members` に最新のメンバー表を、`rosterVersion` を1つ進めて添付します
- 受信側は自分が持つ版数より新しければメンバー表を更新します（最後の送信者に合わせる方式）

### 3.7 取り込み手順（D-19, D-20, D-21）

**取り込みの単位は「会話（スレッド）」です。** らくらくメールから始まった会話に属するメールは、目印が無くても取り込みます。これにより、相手がGmailの画面から普通に返信しても会話が途切れません（SND-04, SND-19）。

**初回取り込み（アカウント登録時）:**

1. 取込範囲を利用者に選ばせる（既定は直近1ヶ月 / D-45, SND-20）
2. `users.messages.list` を `q = "rakurakumail" newer_than:1m in:anywhere` で実行する
   - `in:anywhere` により、自動振り分けで受信トレイをスキップされたメールも対象になります（SND-11）
3. 見つかった各メッセージの `threadId` を集める
4. 各スレッドを `users.threads.get` で取得し、**スレッド内の全メッセージ**を会話として取り込む（目印の無い返信もここで拾われる）
5. 独自ヘッダから会話ID・グループID・送信者名を読み取り、パネルを組み立てる
6. 未登録の相手・未知のグループであれば、パネルを自動作成する（D-38, D-41 / FUN-06）
7. 最新の `historyId` を保存する

**差分同期（アプリ起動時と更新ボタン / D-44, NFR-07）:**

1. 保存した `historyId` を起点に `users.history.list` を実行する
2. 変更の種類ごとに処理する
   - `messagesAdded` … 既知のスレッドなら会話へ追加。未知なら目印の有無を確認し、あれば新規会話として取り込む
   - `messagesDeleted` / `labelAdded(TRASH)` … 会話から削除する（SND-09）
3. `historyId` が古すぎて使えない場合（Googleが保持する期間を過ぎた場合）は、初回取り込みと同じ全件検索にフォールバックする
4. 新しい `historyId` を保存する

**定期ポーリングは行いません。** 常駐せず、通知もしません（D-44, D-46）。

**取りこぼしについて（D-21）:** 相手が「返信」ではなく**新規メール**として送ってきた場合、目印が無ければ検出できません。これは許容します。メールはGmailに残っているため、利用者はGmailで確認できます。

### 3.8 削除（D-47, SND-08, SND-09）

- らくらくメールでメッセージを削除すると、`users.messages.trash` でGmailのゴミ箱へ移します
- Gmail側でゴミ箱へ移されたメールは、次回同期時に差分同期で検出して画面から消します
- **相手側のメールは削除できません。** 削除操作の確認画面にその旨を明記します

### 3.9 相手がらくらくメール利用者かどうかの判定

独自ヘッダ `X-Rakuraku-Version` を持つメールを一度でも受け取った相手を「利用者」と記録します。この情報は次の用途に使います。

- リアクション送信時、フッタに文脈の一文を添えるかどうかの判定（D-32）
- 画面上での表示（「らくらくメール利用中」の小さな印）

リアクション自体は、利用者・未利用者を問わず**常に送ります**（D-29）。

## 4. データ仕様

### 4.1 保存するもの・しないもの（D-48）

| グループとメンバー表 | アクセストークン（メモリのみ / D-54） |
| 会話とスレッドIDの対応 | |
| 同期位置（historyId） | |
| 表示設定・取込範囲 | |

### 4.2 データ構造

```ts
type Account = {
  id: string;                    // UUID
  email: string;
  displayName: string;           // 送信時の差出人名にも使う
  labelIds: { main: string; reaction: string };
  filterIds: string[];
  lastHistoryId: string | null;  // 差分同期の起点
  importRange: '1m' | '3m' | '1y' | 'all';   // 初回取込範囲（D-45）
};

type Contact = {
  id: string;
  accountId: string;             // アカウント単位で保存（D-34）
  email: string;                 // アドレスごとに別の相手（D-37。名寄せしない）
  displayName: string;
  isRakurakuUser: boolean;       // 3.9 の判定結果
};

type Group = {
  id: string;                    // グループID（ヘッダに載せる / D-41）
  accountId: string;
  name: string;                  // 作った人の名前が共有される（D-42）
  members: { email: string; displayName: string }[];
  rosterVersion: number;         // メンバー表の版数（D-43）
  createdByEmail: string;
};

type Conversation = {
  id: string;                    // 会話ID（ヘッダに載せる）
  accountId: string;
  kind: 'direct' | 'group';
  targetId: string;              // Contact.id または Group.id
  subject: string;               // 会話を通じて変えない（3.4）
  threadIds: string[];           // 長いスレッドの分割に対応（3.6）
  lastMessageId: string | null;  // In-Reply-To に使う
  lastActivityAt: string;        // 一覧の並び順に使う
};
```

メッセージ本体はGmailから取得したものをメモリ上に保持し、永続化しません。アプリを閉じれば消え、次回起動時に再取得します。

### 4.3 保存先と暗号化

**第1段階：端末内（D-49 / PER-02）**

- 保存先は IndexedDB
- 値は **AES-GCM** で暗号化して格納する
- 鍵は **Device Key**（`extractable: false` の CryptoKey）を自動生成し、IndexedDB に保持する。利用者の入力操作は一切なし（NFR-01）

**想定する脅威と、守れる範囲を明記します。**

| 脅威 | 守れるか |
| --- | --- |
| PCを覗いた人がブラウザのプロファイルを見る／ファイルをコピーする | **守れる**（鍵はJavaScriptから取り出せず、平文では保存されない） |
| 端末を紛失し、第三者がブラウザを開く | **守れない**（Googleにログインしたままなら中身が見える）→ D-55 のデータ消去機能で対処 |
| このアプリのページ上で悪意あるスクリプトが動く | **守れない**（同一オリジンなので鍵を使える）→ 外部スクリプトを読み込まない方針（6.2）で対処 |

**第2段階：端末間の同期（D-50 / PER-03）**

- 保存先は Google Drive の `appDataFolder`（利用者のドライブ内の非表示領域）
- **Sync Key**（AES-GCM、取り出し可能）で暗号化した1つのファイルとして保存する
- Sync Key は端末内では Device Key で包んで（`wrapKey`）保管する
- 同期のタイミングは、設定変更時と同期実行時。競合したときは**更新時刻の新しい方を採用**し、古い方の内容は差分として画面に提示する

**第3段階：パスキー（D-52 / PER-06）`[TBD]`**

WebAuthn の PRF拡張から Sync Key を導出する方式。対応状況を見て導入時期を決めます。

### 4.4 移行コード方式（D-51 / PER-04）

2台目の端末が Sync Key を受け取るための手順です。**鍵そのものをDriveに置かない**ため、Googleアカウントが破られても設定データは読めません。

```
【1台目】                                  【2台目】
1. 「別の端末を追加」を選ぶ
2. 使い捨ての移行コードを生成
   （128ビット乱数 → 8文字の英数字）
3. コードから包み鍵を導出 (HKDF)
4. Sync Key を包んで Drive の
   appDataFolder に transfer.tmp として保存
5. QRコードと8文字を画面に表示  ────────▶ 6. QRを読み取る、または8文字を入力
                                            7. 同じ手順で包み鍵を導出
                                            8. transfer.tmp を取得して開く
                                            9. Sync Key を取得
                                           10. 設定データを復号して取り込む
11. transfer.tmp を削除                  ◀── 完了を確認
```

- `transfer.tmp` は**10分で自動削除**します（1台目のアプリが削除。取得後は即時削除）
- 8文字（約40ビット）で十分な理由: `transfer.tmp` は利用者自身のDrive内にあり、**Googleアカウントへのアクセス権がなければ総当たりの対象にすらできない**ためです
- QRコードが読めない環境のために、8文字の手入力も必ず用意します（NFR-01）

### 5.5 デザイン方針（DES-01 / D-56, D-57, D-60）

**避けるもの:** 4色混在（Slack）、黄緑基調（LINE）。

**方向性:** 藍色を基調に、朱色を差し色として1色だけ使う。落ち着いた和の配色で、SlackともLINEとも印象が重なりません。

**色トークン（D-60 で確定）**

| トークン | 色 | 用途 |
| --- | --- | --- |
| `--bg` | 生成り `#F7F4EF` | 画面の地 |
| `--surface` | 白 `#FFFFFF` | 相手の吹き出し、入力欄、一覧の行 |
| `--primary` | 藍 `#28417A` | ヘッダ、自分の吹き出し、リンク |
| `--on-primary` | 白 `#FFFFFF` | 藍の上の文字 |
| `--accent` | 朱 `#D2553F` | 新着の印などの差し色。**文字を載せない** |
| `--accent-strong` | 濃朱 `#C0442F` | 送信ボタンなど、**白文字を載せる**面 |
| `--text` | 墨 `#22252A` | 本文 |
| `--text-sub` | 鼠 `#5A6070` | 時刻・補助文 |
| `--border` | 砂 `#DED8CC` | 罫線、吹き出しの枠 |

**朱を2トーンに分ける理由:** 白文字を朱 `#D2553F` に載せるとコントラスト比が 4.1:1 となり、5.4 が定める 4.5:1 を満たしません。白文字を載せる面には濃朱 `#C0442F`（5.1:1）を使います。朱 `#D2553F` は文字を載せない差し色（新着の印など）に限って使い、生成り上で 3.8:1 のため非文字UIの基準 3:1 を満たします。

**コントラスト比の実測値（5.4 の基準に対する検証結果）**

| 組み合わせ | 比 | 判定 |
| --- | --- | --- |
| 白 on 藍 `#28417A` | 9.9 : 1 | ◎ |
| 白 on 濃朱 `#C0442F` | 5.1 : 1 | ◎ |
| 墨 `#22252A` on 生成り `#F7F4EF` | 14.0 : 1 | ◎ |
| 墨 `#22252A` on 白 | 16.0 : 1 | ◎ |
| 藍 `#28417A` on 生成り | 9.0 : 1 | ◎ |
| 鼠 `#5A6070` on 生成り | 5.7 : 1 | ◎ |
| 朱 `#D2553F` on 生成り（非文字UI） | 3.8 : 1 | ◎（基準 3:1） |

**文字サイズ:** 本文の既定は 18px（5.4）。`--font-size-base` を CSS変数として定義し、「大」22px /「特大」26px に切り替えられる形にします。切替UIの実装はM8です。

**アイコン:** 封筒と吹き出しを組み合わせた図形を基本形にします。UI内のアイコンは線の太さを揃えた単色の線画で統一します。ロゴとアイコン一式の両方を作成します（D-56）。ロゴとアイコンの具体案はM8で扱います。

### 6.3 エラー処理

| 事象 | 挙動 |
| --- | --- |
| トークン取得失敗 | ログイン画面へ誘導。「Googleへのログインが切れました」と表示 |

| 送信失敗 | 吹き出しを「送信できませんでした」状態で残し、**再送ボタン**を出す。入力内容は失わない |
| 同期失敗 | 前回の内容を表示したまま、上部に控えめな警告バーを出す。画面は白紙にしない |
| オフライン | 送信を禁止し、閲覧は直前の内容を表示する |
