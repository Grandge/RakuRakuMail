## 1. 実装前に決着させること

要件定義書 9章のうち M1 に関わる3件です。**ここが承認されてから Step 1 に入ります。**

### 1-1. `gmail.modify` に `messages.send` が含まれるか（未確定事項1 / `[要検証]`）

**現時点の見立て: 含まれる。** Gmail API リファレンスの `users.messages.send` は、認可スコープとして `https://mail.google.com/` / `gmail.modify` / `gmail.compose` / `gmail.send` の4つを挙げています。したがって `gmail.modify` 単独で送信できるはずです。

ただし文書上は `[要検証]` のままなので、**Step 3（最初の送信）で実地に確認**します。所要5分です。

- 送信が通れば → M1〜M8を通じて `gmail.modify` 1本で足ります。スコープが増えないので同意画面の文言も軽くなります
- `403 Insufficient Permission` が返ったら → `https://www.googleapis.com/auth/gmail.send` を追加し、要件定義書 2.4 の表と決定事項を更新します

補足として、`gmail.modify` には **フィルタの作成権限は含まれません**（`gmail.settings.basic` が別途必要）。これは要件定義書 2.4 の記載どおりで、M2 で追加します。

### 1-2. 件名の形式（未確定事項4 / `[要承認]`）

相手の受信箱に出る文字列です。3案出します。

| 案                                    | 1対1の件名                               | グループ（M5）の件名       | 評価                                                                                                                          |
| ------------------------------------- | ---------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **A（要件定義書のまま・推奨）** | `らくらくメール（芝 直之）`            | `らくらくメール（家族）` | 1対1とグループで形が揃う。実装が最も単純                                                                                      |
| B                                     | `らくらくメール`                       | `らくらくメール（家族）` | 差出人名と重複しないぶん簡潔。ただし同じ相手と2つ目の会話を始めたとき、Gmail側が件名で同一視して1スレッドに見せる可能性がある |
| C                                     | `らくらくメール：芝 直之 と 山田 花子` | `らくらくメール（家族）` | 未利用者の受信箱で「誰と誰のやり取りか」が一目で分かる。ただし長く、1対1とグループで形が崩れる                                |

**推奨は A（要件定義書のまま）です。** 理由は3つです。

1. 案Bの「同じ相手との2つ目の会話が混ざる」問題を、案Aは開始者名で部分的に避けられる（相手が違えば件名も違う）
2. 案Cは受信箱では親切ですが、件名は会話を通じて固定（3.4）なので、**あとから表示名を変えても件名は変わりません**。2人分の名前を焼き付けると陳腐化しやすくなります
3. グループ（M5）の `らくらくメール（家族）` と形が同じで、利用者にも実装にも一貫します

Aの弱点は「差出人名と件名で同じ名前が2回出る」ことですが、受信箱の見た目が少し冗長になるだけで実害はありません。

> 案Aで進めてよければ「A」とだけお返しください。B・Cをご希望なら、要件定義書 3.4 とグループ側の記述を合わせて更新します。

### 1-3. 配色（未確定事項6 / `[要承認]`）

### 手順

**Step 0-1. プロジェクトを作る**

1. https://console.cloud.google.com/ を開く。右上のアカウントが **A** になっていることを確認する（違えば切り替える）
2. 画面上部、Googleロゴの右にあるプロジェクト選択メニュー（初回は「プロジェクトを選択」）をクリック
3. ダイアログ右上の **「新しいプロジェクト」** をクリック
4. 「プロジェクト名」に `rakurakumail` と入力。「場所」は「組織なし」のままでよい
5. **「作成」** をクリック。数十秒で作成される
6. 作成後、画面上部のプロジェクト選択メニューが `rakurakumail` になっていることを確認する（なっていなければ選び直す）

> 以降のすべての操作で、**上部のプロジェクトが `rakurakumail` であること**を毎回確認してください。別プロジェクトで設定してしまうのが最も多い事故です。

**Step 0-2. Gmail API を有効にする**

1. 左上のハンバーガーメニュー（≡）→ **「API とサービス」** → **「ライブラリ」**
2. 検索欄に `Gmail API` と入力して選ぶ
3. **「有効にする」** をクリック

M1で有効化が必要なのは **Gmail API だけ** です。以下は将来のためのメモで、**今は有効にしないでください**（スコープが増えると同意画面の文言が重くなるため）。

| API              | 有効化する時期                      |
| ---------------- | ----------------------------------- |
| Gmail API        | **M1（今）**                  |
| Google Drive API | M6（Drive同期）                     |
| People API       | M3以降（連絡帳から相手を選ぶ / P2） |

Google Identity Services（ログイン）は API の有効化を必要としません。

**Step 0-3. OAuth の対象ユーザーを設定する（同意画面）**

1. 左メニュー → **「Google Auth Platform」**（見当たらなければ「API とサービス」→「OAuth 同意画面」）
2. 未設定なら **「開始」** を押す
3. **アプリ情報**
   - アプリ名: `らくらくメール`
     - ここに入れた名前が **同意画面に表示されます**。相手役Bのアカウントでログインしたとき「らくらくメール が Google アカウントへのアクセスを求めています」と出ます
   - ユーザーサポートメール: A のアドレスを選ぶ
4. **対象**（Audience）
   - **「外部」** を選ぶ。個人のGmailアカウントを使うため（D-06）、「内部」は選べません
5. **連絡先情報**: A のアドレスを入力
6. 規約に同意して **「作成」**

**Step 0-4. テストユーザーを登録する（D-08）**

1. 「Google Auth Platform」→ **「対象」**（Audience）
2. 公開ステータスが **「テスト」** になっていることを確認する（「本番環境」になっていたら「テストに戻す」）
3. 下部の **「テストユーザー」** → **「+ Users」**
4. **A と B の両方のGmailアドレス** を登録する
   - **A も必ず登録してください。** プロジェクトのオーナーであっても、テストモードではテストユーザーに入っていないとログインが `access_denied` で弾かれます
5. 「保存」

> テストモードの上限は100人です。D-07の「10人程度」は十分に収まります。

**Step 0-5. スコープを登録する**

1. 「Google Auth Platform」→ **「データアクセス」**（旧画面では「OAuth 同意画面」内の「スコープ」）
2. **「スコープを追加または削除」** をクリック
3. 一覧の検索欄に `gmail.modify` と入力し、`https://www.googleapis.com/auth/gmail.modify` にチェックを入れる
   - 「制限付きスコープ」の区分に入っています。テストモードでは制限付きスコープも使えます
4. **「更新」** → **「保存」**

M1で登録するのはこの1つだけです。1-1の検証結果しだいで `gmail.send` を足します。

**Step 0-6. OAuth クライアント ID を作る**

1. 「Google Auth Platform」→ **「クライアント」**（旧画面では「API とサービス」→「認証情報」）
2. **「+ クライアントを作成」**
3. アプリケーションの種類: **「ウェブ アプリケーション」**
4. 名前: `らくらくメール Web`（管理用の名前。利用者には見えません）
5. **「承認済みの JavaScript 生成元」** に、次を **「+ URI を追加」** で登録する

   | URI                                 | 用途                              |
   | ----------------------------------- | --------------------------------- |

### Step 3. メールを1通送る ← **未確定事項1の検証地点**

### Step 4. メールを取り込む

`mail/quote.ts` → `mail/parse.ts` → `gmail/threads.ts` → `domain/importer.ts`

- `messages.list?q=rakurakumail in:anywhere newer_than:1m`

- スレッド内の全メッセージを解析し、`Message` の配列にする

- 本文からフッタと引用部分を落とす

**確認:**

2. 本文にフッタが **含まれていない**

4. **BのGmailの画面から普通に返信** し、Aで取り込むと **その返信も同じスレッドに入っている**（D-19の核心。返信には目印が無いが `threadId` が同じなので拾える）

6. 日本語が文字化けしていない（`quoted-printable` と `base64` の両方の本文で確認。Gmailウェブ版が返信を送るときの符号化方式に依存します）

### Step 7. 落ち穂拾い（エラー処理）

要件定義書 6.3 のうち、M1に必要なもの。

- トークン失効 → 401 を捕まえて再取得し、1回だけ再試行。だめならログイン画面へ
- レート制限 → 429/5xx で指数バックオフ、最大3回（6.3）
- 送信失敗 → 吹き出しを「送信できませんでした」状態で残し、**再送ボタン** を出す。**入力内容を失わない**
- オフライン → `navigator.onLine` を見て送信を止める
- 同期失敗 → 画面を白紙にせず、上部に控えめな警告バーを出す
- エラー文言は5.4に従い「次に何をすればよいか」を1文で書く（「エラーが発生しました」で終わらせない）

**確認:**

1. DevTools の Network を Offline にして送信 → 「インターネットに繋がっていません。繋がってからもう一度お試しください」等が出て、入力内容が残る
2. `session.ts` のトークンを手で壊す → 401 が起き、自動で取り直して送信が成功する
3. Networkスロットリングを最遅にしても画面が固まらない

### Step 8. 永続化（4.3 第1段階）

`store/deviceKey.ts` → `store/crypto.ts` → `store/db.ts`

- `crypto.subtle.generateKey('AES-GCM', **extractable: false**, ['encrypt','decrypt'])` で Device Key を作る

- M1で保存するのは `Account` と `Contact` のみ

**確認:**

1. 相手を登録 → ページ再読み込み → 相手が残っている
2. DevTools → Application → IndexedDB で中を見て、**保存された値が読めないバイト列になっている**
3. 同じ画面で鍵のレコードを見ると `CryptoKey` で、`extractable: false`
4. IndexedDBを消して再読み込みしても、アプリが落ちずに初期状態から始まる

### 認証まわり

| #  | 症状                                                                                                                      | 原因と対処                                                                                                                                                                                                                                                                                                                                                         |
| -- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1  | `Error 400: redirect_uri_mismatch` / `origin_mismatch`                                                                | JavaScript生成元の文字列が完全一致していない。**末尾スラッシュ**、`http`/`https`、`localhost`/`127.0.0.1`、ポート番号を確認。ブラウザのoriginは**入力したホスト名がそのまま**使われるため、`127.0.0.1` を登録したなら `localhost` で開いてはいけない。Viteが5173を取られて5174で起動していると必ず起きるので `strictPort: true` を入れる |
| 1b | 生成元の登録時に「**無効な生成元: 末尾はパブリック トップレベル ドメイン（.com、.org など）にする必要があります**」 | Google Cloud Console の「クライアント」画面が`http://localhost:5173` を拒否する。**`http://127.0.0.1:5173` を登録する**（IPアドレスは通る）。それも拒否された場合は、ループバックに解決する公開ドメイン `http://lvh.me:5173` を使い、Viteの `server.host` を `lvh.me` に合わせる                                                                   |
| 1c | `npm run dev` が `Port 5173 is already in use` で落ちる                                                               | `strictPort: true` のため、前回のViteが残っていると起動しない。`Get-NetTCPConnection -LocalPort 5173 -State Listen` でPIDを調べて `Stop-Process` する                                                                                                                                                                                                        |
| 2  | `Error 403: access_denied`（「Google の審査プロセスを完了していません／承認されたテスターのみがアクセスできます」） | ログインしようとしたアカウントがテストユーザーに入っていない。**プロジェクトのオーナー自身も登録が必要**（Step 0-4）。確認には **クライアントIDの先頭の数字＝プロジェクト番号** を使うのが確実で、`https://console.cloud.google.com/auth/audience?project=<プロジェクト番号>` を開けば、そのクライアントIDを持つプロジェクトの画面が必ず開く（プロジェクトを取り違えて別の場所に登録していた場合もここで分かる）。登録済みに見えるのに直らないときは、(a) 画面上部のプロジェクトが違う (b) 保存が効いておらず、ページを再読み込みすると消えている (c) エラー画面の「エラーの詳細」で実際に使われたクライアントIDを確認する、の順に疑う。反映に1分ほどかかることがある |
| 3  | 起動時の裏取得が**ポップアップブロック** で失敗する                                                                 | GISのトークンモデルは`prompt: ''` でもポップアップウィンドウを開きます。ユーザー操作を伴わない起動直後の呼び出しはブラウザに塞がれることがあります。**これは仕様どおりの流れ（2.3 手順3）で吸収します** — 失敗したら「Googleでログイン」ボタンを出し、クリック（＝ユーザー操作）で呼び直す。M1ではこの2段構えを必ず実装してください                       |
| 4  | 1時間後に突然 API が 401 を返す                                                                                           | トークンの寿命。残り5分で先回りして取り直す。ただし再取得もポップアップ経由なので、直前にユーザー操作が無いと塞がれます。**401を捕まえて「もう一度ログインしてください」を出す経路も必ず用意する**（#3と同じ理由）                                                                                                                                           |

### メールの組み立て・解析まわり

| #  | 症状                                                         | 原因と対処                                                                                                                                                                                                                                                                               |
| -- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 7  | `400 Invalid value at 'message.raw'`                       | Gmail APIの`raw` は **base64url**（`+`→`-`、`/`→`_`、`=` は削る）です。素の base64 だと弾かれます                                                                                                                                                                    |
| 8  | 送信した日本語本文が文字化けする                             | `btoa()` は Latin-1 しか扱えません。`TextEncoder` でUTF-8のバイト列にしてから base64url にすること。逆方向は `atob` の結果を `Uint8Array` にして `TextDecoder('utf-8')`。**`escape`/`unescape` を使った古い定石は使わないでください**                                |
| 9  | 件名だけ文字化けする                                         | メールヘッダはASCIIしか通りません。日本語の件名と差出人表示名は**RFC2047**（`=?UTF-8?B?<base64>?=`）で符号化が必要です。本文とは別処理なので忘れやすい箇所です                                                                                                                   |
| 10 | `400 Invalid thread_id value`                              | `threadId` を指定した送信では、Gmailが「本当に同じ会話か」を件名と `References` で照合します。**件名を変えない**（3.4）ことと `In-Reply-To`/`References` を正しく入れることの両方が要ります                                                                                |
| 11 | `In-Reply-To` に何を入れるか分からない                     | `messages.send` の応答の `id` は Gmail 内部IDで、RFC822の `Message-ID` とは別物です。送信後に `messages.get?format=metadata&metadataHeaders=Message-ID` で取り直す必要があります（Step 6）。`Conversation.lastMessageId`（4.2）に入れるのはこちらです                          |
| 12 | 独自ヘッダが受信側で消えている                               | Step 3 の確認#5 で必ず目視。もし消えていたら 3.3 の前提が崩れるので、設計変更の判断が要ります                                                                                                                                                                                            |
| 13 | 相手の返信を取り込むと、過去のやり取り全部が本文に入っている | Gmailの返信は元メールを引用します。`>` で始まる行、`On ... wrote:` /「2026年9月1日(月) ... :」のような引用ヘッダ行を落とす処理が要ります（`mail/quote.ts`）。メールソフトごとに形が違うので、**完全を目指さず、Gmailウェブ版とGmailアプリの形だけ対応** して残りは許容します |
| 14 | 受信本文の改行がおかしい /`=E3=81=82` のような文字列が出る | `quoted-printable` を復号していない。Gmailウェブ版は本文に応じて `base64` と `quoted-printable` を使い分けます。**両方への対応が必要** です（`Content-Transfer-Encoding` を見て分岐）                                                                                      |
| 15 | `threads.get` の `payload` の構造が思ったのと違う        | 本文の入り方が`payload.body.data` の場合と `payload.parts[]` を再帰的に辿る場合があります。`multipart/alternative` では `text/plain` と `text/html` の両方が入るので、**`text/plain` を優先して選ぶ** 再帰探索を書きます                                               |

### 動作確認まわり（テストのやり方で詰まる）

| #  | 症状                                                                     | 対処                                                                                                                                                                                                                       |
| -- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
